# Augur 本次更新说明

> 面向用户的功能说明（非技术变更日志，技术细节见 [CHANGELOG.md](../CHANGELOG.md)）。

## 这次更新解决了什么问题

用户实测反馈了三个问题："首页仪表盘根本点不动""很多地方数据都不显示""投委会、深度报告这一块也有问题"。v10.16.4 先修了投委会里 Kelly 仓位显示错误（1990.0% 这种明显错误的数字）；v10.16.5 修了首页相关的 11 个接口卡死事件循环的问题。这次（v10.16.6）把同一个根因排查到了投委会和深度报告自己的代码路径上——**但实测发现这次只是大幅缓解，不是彻底解决**，详见下面"已知局限"。

根因和 v10.16.5 完全一样：`analyze_ticker`（单标的全量分析）、`report_ticker`（深度报告）、`api_committee`（投委会）、`api_compare`（对决）、`api_debate`（辩论）等 8 个接口被声明成 `async def`，但函数体里从头到尾没有一处 `await`——内部做的是同步阻塞的 yfinance 网络请求，外加 18 位投资大师的同步分析计算。Dashboard 是单进程单事件循环跑的，生成一次投委会结论或深度报告期间，这个事件循环会被整段占住，服务器当时在处理的所有其他请求（包括其他用户、其他页面的点击）都会被一起拖住。

另外两个流式接口（`/ws/analyze`、`/ws/committee`）因为协议要求必须保持 `async def`，没法用同样的办法改成同步函数，所以用了线程池把里面阻塞的网络请求单独丢出去执行。

## 修复内容

- 上述 8 个接口（单标的分析、深度报告、投委会、对决、辩论、人格对比、单人格观点、自选股批量分析）从 `async def` 改成普通的同步函数，交给 FastAPI 的线程池执行，不再占用事件循环。
- `/ws/analyze`、`/ws/committee` 这两个 WebSocket 接口里阻塞的 yfinance 调用改用线程池执行（`run_in_threadpool`），同样不再占用事件循环，但接口本身保持 `async def` 以满足 WebSocket 协议要求。
- 顺手修了一个潜在的隐藏 bug：`analyze_ticker` 里原来靠 `asyncio.get_event_loop()` 把通知规则派发到后台执行，这个写法只在「主线程持有正在运行的事件循环」时才靠得住——一旦这个接口改成同步函数后被丢进线程池执行，这行代码会直接报错（被旁边的 `except Exception` 默默吞掉），导致规则通知静默失效。改成普通的后台线程后，语义不变，且不再依赖事件循环是否存在。
- 扩大了回归测试覆盖范围：结构性测试现在覆盖 19 个接口（v10.16.5 时是 11 个），断言它们必须保持同步 `def`，防止以后再被误标成 `async def`。

## 已知局限（这次没有完全解决）

接口改成同步函数之后，我们没有只看"结构对不对"就收工，而是重新跑了真实并发压测——结果发现：投委会运行期间（18 位投资大师全跑一遍），别的请求确实不会再被无限期卡住了，但仍然会被拖慢 3 秒以上，有时甚至比投委会自己的耗时还长。单独测 5 个并发的快接口（不带投委会）完全正常，最慢 21 毫秒，说明线程池本身没问题。

真正的根因和 v10.16.5 不一样：18 位投资大师的 `analyze()` 是纯 CPU 计算，不是网络 I/O。把 CPU 计算丢进线程池并不能让它在 Python 里真正并行——CPython 同一时刻只有一个线程能拿到 GIL（全局解释器锁）执行代码，一个线程长时间占着 GIL 做重计算，会让其他线程的请求被严重拖慢，这是 CPython 里有名的"GIL 护航效应"。要彻底解决，需要给 `analyze()` 本身做性能优化，或者把它挪到真正能并行的地方（比如进程池、或者让服务器跑多个独立进程）——这两种都是更大的改动，会涉及到内存里的单例状态、缓存、限流计数器要怎么在多进程间共享，目前先不做，等用户确认方向。

这次的实际效果是：投委会/深度报告生成期间，不会再让整个 Dashboard 服务器完全瘫痪到底（原始 bug 已经没有了），但其他用户/其他页面在那几秒内仍然会感觉到明显的卡顿。

## 测试情况

完整测试套件 **2095 个测试全部通过**（不含需要网络访问的 5 个测试；算上的话是 2100 个），没有失败项。

## 这次是怎么发现的

v10.16.5 修完首页 11 个接口后，针对同一根因模式做了一次全量复查：把 `dashboard/app.py` 里所有声明成 `async def` 但内部直接调用 `fetch_market_context` 或投资大师分析的函数都列出来比对——结果发现投委会、深度报告这条路径上还有 8 个接口、2 个 WebSocket 接口存在完全相同的问题，而且恰好就是用户报告里点名的"投委会""深度报告"板块。
